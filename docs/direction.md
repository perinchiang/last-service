# LAST SERVICE — 方向与原型约定

本文记录 2026-11-16 确认的设计方向；2026-11-17 随 v0.1.2 原型更新实现状态。后续区域和敌人仍是候选方向，不代表已经制作。

## 核心设想

Unit 07 是一台人形维修机器人。人类已经离开，设施仍执行回收协议。它醒来后先扫描环境，推断值班主管失联，再寻找人类授权以离开设施。门禁因缺少主管签署而拒绝放行。

Unit 07 的 MK.04 是维修脉冲器，不是突然出现的普通步枪。它原本用于切断联锁、拆解卡死部件和维护设施；维护输出可用，但对安保目标的发射权限需要人类批准。安保单元部署、威胁迫近时，Unit 07 自身的安全控制器触发临时自卫例外。设施负责下达回收命令，本机负责自我保护，两者不是同一个授权来源。机器可以用工具保护自身，但系统会记录未经授权的自主行动。

玩家以第一人称操作。角色不需要完整的写实骨骼或复杂全身步行动画；武器、前臂、换件和交互动作承担主要角色表现。环境、无人机、设备和 UI 均以代码生成的几何、程序材质和程序动画为主。

## 核心战斗

这是封闭设施内的第一人称动作游戏，不是 QTE 驱动的过场游戏，也不要求把机关做成传统谜题。玩家在实时战斗中观察敌人和设施，决定先射击敌人，还是射击设备改变战况。吊箱锁扣是第一种环境武器：射断锁扣可让货箱落下，砸击附近目标并成为新的掩体或障碍。

每个未来区域应改变战斗中的一个选择，而不只是换颜色和布景。冷却管、闸门、供电或移动货物可成为后续候选；在玩家验证第一间大厅的玩法前，不增加新区域。

## 诊断 UI

机器人界面表达“感知 → 工具调用 → 结果 → 推断 → 目标”，但这是预先编排的游戏内系统日志，不是实际运行 Python，也不逐帧展示游戏函数。

- 启动时，镜头先保持在维修平台上。左侧逐行显示感知与诊断，右侧显示设施时间、温度、照明、机体完整度、工具连接状态、人类信号和发射权限。目标形成后，平台才下降、检修臂才收回，玩家随后接管。开场共约 10.8 秒，前 7.4 秒保持躺卧；目标先形成，检修装置再运动。开场可跳过，跳过后任务与工具状态保持一致。
- 玩家移动和射击时不记录每个按键。当前目标、工具和权限作为状态持续显示；事件日志只在有意义的状态变化时出现，例如门禁拒绝、联锁解除、敌人部署、环境机关改变战斗、目标更新。普通日志最多约每 30 秒汇总一次，没有行动就不凑日志；关键事件立即显示，约 7 秒后事件面板退场。同一终端重复检查不反复记录拒绝信息。
- 诊断流采用受控的光学 HUD：细线、分段框和扫描标记，使用克制的冷色系统信息、琥珀色操作提示和红色威胁提示。中心准星与战斗视野保持清晰。游戏中右侧只保留设施时钟与工具权限，完整度和电容余量由原有战斗 HUD 显示；手机竖屏将这两项收成一行，事件只展示最新一条，避免与触控区争抢空间。
- 设施时钟可显示“未同步”，并将温度等扫描结果用于营造停运环境；不要显示与剧情无关的实时主机日期，也不要虚构会影响战斗但实际不存在的电量系统。当前原型以完整度和脉冲器余量反映状态。

## 当前进度与下一步

v0.1.2 原型包含一间维修大厅、门禁联锁、两波安保无人机、可射落的吊箱、开门逃离流程，以及完整的“自检 → 建立目标 → 起身”开场。`src/archive-world.js`、`src/hound.js`、`src/hound-motion.js`、`src/record-state.js` 是未跟踪草稿；本轮不会把它们并入发行流程。

本轮已落地的流程：

1. 机器人醒来后先读取环境和设施时钟，不立即起身。
2. 诊断得出“寻找值班主管”的目标，并显示维修工具已接入、战斗权限仍锁定。
3. 机器人起身后前往终端；门禁拒绝放行并要求人类授权。
4. 玩家用维修脉冲器解除联锁，安保无人机响应，临时自卫权限启用。
5. 玩家可以正面射击，也可以利用吊箱改变战斗局面，击退威胁后手动开启出口。

下一轮先试玩已有大厅，暂不扩成开放区域或多房间。重点观察：玩家是否理解自己要寻找的人，是否看懂权限变化，是否主动尝试吊箱，以及结束后是否愿意再玩一次。

根据试玩结果优先调整敌人的接近路线、吊箱时机、攻击预警与命中反馈。如果玩家仍只是站着射击，就先修战斗中的选择，不以新增房间或更复杂机器人掩盖问题。等单厅的选择成立，再制作同一栋设施内的少量互通功能区。
